# CoreScope v3.10.0 — The Diet

**Upgrade urgency: High for anyone running without a `packetStore` config
block.** On a default config the in-memory packet store is unbounded, and this
release is the one that tells you so. 66 commits since v3.9.2.

---

## ⚠️ Read this before upgrading

### 1. Check your `config.json` for a `packetStore` block

If you don't have one, **your in-memory store is unbounded** — and always has
been. `retentionHours` and `maxMemoryMB` both default to `0`, meaning
*unlimited*, and the eviction ticker is a no-op when both are zero. The store
loads your entire database into RAM and never evicts.

On a small mesh you may never notice. On a busy one it ends the same way every
time: RSS climbs to `GOMEMLIMIT`, the GC begins running continuously, API
latency goes from milliseconds to tens of seconds, and something restarts the
container. We measured a production instance doing this **~104 times a day**.

Add this and restart:

```json
"packetStore": {
  "retentionHours": 72,
  "maxMemoryMB": 900
}
```

That one change took the instance above from **4,809 MB RSS to ~1,920 MB** and
from ~104 restarts/day to zero. Everything else in this release is smaller than
that — please do this first.

### 2. `maxMemoryMB` now means what it says

The store's self-accounting under-counted real heap by ~40%. It charged a flat
200 bytes per *transmission* for two dedup maps that actually grow per
*observation* (production averages ~25 observations per transmission, with
109-byte keys), and it measured raw string lengths while ignoring the Go
allocator's size classes.

Measured against live heap it was **0.62×**. It is now **1.01×**.

**Practical effect: your store will hold less than it did**, because the cap is
finally honest. If you tuned `maxMemoryMB` empirically against the old
behaviour, raise it by roughly 1.6× to keep the same working set.

### 3. `retentionHours` now means "active within", not "first seen within"

Eviction used to cut on `first_seen`, which is written once and never updated.
That discarded long-lived packet hashes still receiving traffic — the loader
fetched them at startup (correctly, per #1690) and eviction dropped them seconds
later. On a production instance: **813,545 observations loaded, 194,829 evicted
within 30 seconds — 24% of cold-start work wasted, every restart.**

Eviction now judges by most-recent activity, matching what the loader selects.

**Effect: at the same `retentionHours` you retain ~25% more.** That is the bug
being fixed rather than a regression, but budget for it.

## What `retentionHours` actually controls

A common misreading, so to be explicit: **it bounds the in-memory store, not
your database.** SQLite keeps everything until `retention.packetDays` prunes it
(disabled by default).

Bounded by `retentionHours` — served from the store: the packet feed and its
filters, the live map and VCR replay, the analytics tabs.

**Not** bounded by it — served from SQLite directly: packet permalinks (they
fall back to the DB explicitly), channel chat history, traces, observer metrics,
and node data.

So a 72-hour store does *not* mean 72 hours of visible history.

## 📉 Memory

- **Per-observation `raw_hex` dropped** (#1773) — every observation carried a
  full copy of its parent transmission's frame. Roughly 98 MB of pure
  duplication and ~1.7M redundant allocations on a live store. The read path
  already fell back to the transmission, so nothing is lost. Measured on
  production: **1,920 MB → ~1,310–1,740 MB** (the range is GC sawtooth) on an
  unchanged dataset and config.
- **Honest store accounting** — see upgrade note 2.
- **`/api/perf?mem=1`** (#1773) — opt-in per-component breakdown of what the
  store actually holds. It walks the store under a read lock, so poll it on
  demand, not from a dashboard.
- **Eviction no longer pins evicted transmissions.** The packets slice was
  compacted by trimming, leaving stale pointers in the backing array past the
  new length; those kept every evicted transmission and its whole observation
  list reachable until new packets happened to overwrite the slots.

## 🔒 Security

**The `/ws` WebSocket no longer accepts every origin** (#1793). It previously
returned `true` unconditionally, so any website could open a socket and stream
your live packet feed.

Now: same-origin allowed, empty `Origin` (non-browser clients) allowed, anything
else must appear in `corsAllowedOrigins`. `"*"` is deliberately ignored for
WebSockets even though CORS XHR still honours it.

**If you front CoreScope with a reverse proxy, confirm it preserves the `Host`
header** (`proxy_set_header Host $host` in nginx). If it rewrites Host,
same-origin detection fails and the live view silently stops updating.

## ✨ New features

- **Mobile client-RX coverage** (#1728) — opt-in, off by default. Companion apps
  publish GPS-tagged receptions to build a crowdsourced RF reach map. Requires
  an ACL-capable broker; without ACLs the GPS is spoofable. See
  `docs/client-rx-coverage.md`.
- **"My Repeaters" dashboard** (#1761) — favourite repeaters, monitor them on
  one page.
- **Repeater usefulness score** (#1762) — the full four-axis score.
- **Transported region scopes** in the repeater sidebar (#1751).
- **"Multibyte only" live filter** (#1780).
- New per-node API fields `flood_advert_count_7d` (#1831) and
  `unscoped_relay_count_24h` (#1823); a `routed_through` filter; autocomplete
  for `payload.destHash` / `payload.srcHash` (#1774).

## 🔍 Decoder correctness

CONTROL `DISCOVER_REQ`/`RESP` subtypes and body fields (#1802) · GRP_DATA
channel hash plus inner `data_type`/`len`/`blob` (#1792) · Group Data,
Multipart, Control and Raw Custom added to the packet type filter (#1791,
#1798) · firmware-default Public channel (`0x11`) preserved in analytics
(#1729) · Relay Airtime Share now uses preamble-aware LoRa time-on-air (#1768)
· TRACE Hop Bytes column no longer mislabels SNR as hop hashes (#1849).

## 📡 Reliability

- **MQTT watchdog hardening** (#1749, #1810) — escalates persistent paho
  disconnects, recovers from an emit panic, exposes a watchdog tick. Targets the
  failure where the broker connection dies silently and ingest freezes while the
  container still reports healthy.
- **Background loader gated on chunked-load completion** (#1809).
- **Ingest-freshness watchdog** shipped in `deploy/` — a reference systemd timer
  that restarts CoreScope when no packet has arrived in N minutes. It
  distinguishes "the API is unreachable" (restart the container) from "ingest is
  stale" (recycle only the ingestor), and stands down during cold start.

## Upgrading

```bash
docker compose pull
docker compose up -d
```

No schema migration blocks startup. Watch your first cold load — it now reports
coverage explicitly:

```
[store] LoadChunked: 23754 transmissions (813545 observations) in 1m5s
[store] RunStartupLoad: coverage=15.3%, loaded=23754, totalInDB=155564
```

A low `coverage` means `retentionHours` is tighter than your database. That is
fine and intentional, but worth knowing.

**Pin your image.** `latest` only moves when a release is cut — tracking a tag
that hasn't moved is how an instance ends up months behind without anyone
noticing. Pin a version tag or a digest and update deliberately.
